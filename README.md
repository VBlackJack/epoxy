# EPOXY - Grid Logic Puzzle Game

*Version française : [README.fr.md](./README.fr.md)*

**Play online:** [https://vblackjack.github.io/epoxy/](https://vblackjack.github.io/epoxy/)

**EPOXY** is a web-based tile puzzle game in the spirit of the handheld puzzlers of the Atari Lynx era, built with TypeScript, HTML5 Canvas, and the Web Audio API.

## Features

- **Hundreds of Levels Included**:
  - **Epoxy Campaign**: 30 hand-written levels grouped in chapters (defined in `public/configs/campaign.json`), each built around one idea and proven solvable by replaying its recorded solution in the game engine. They teach one mechanic per level, from chips, keys and boots to traps, cloners, creatures, thieves, item barriers, turtles and flame jets, and each chapter ends with a level that combines them. An originality test keeps every map unlike the bundled community levels. The Levels dialog shows the campaign by chapter, each collapsible, with a progress bar and an overview strip that jumps to a chapter, and a chapter's title appears when you start its first level.
  - **Buried Sanctuaries Campaign (`epoxy_excavation`)**: 20 subterranean excavation levels grouped into 5 chapters (`public/configs/excavation-levels.json` and `public/configs/excavation-campaign.json`) built around earth veins (`dirt`), boulder sluices (`dirt_block` and `water`), counterweights (`pressure_plate_*` and `hold_door_*`), grappling alcoves (`boots_pull`), and buried laser prisms (`laser_emitter_*`, `mirror_slash`, `mirror_backslash`, `laser_receiver_*`, `laser_gate_*`), each proven solvable with its stored solution (`O`) and an isolated save slot. See the [Sanctuary Puzzle & Mechanism Encyclopedia](./docs/puzzle-encyclopedia.md) ([version française](./docs/fr/puzzle-encyclopedia.md)) and `public/configs/excavation-encyclopedia.json` for the 25 canonical puzzle archetypes across 9 families (`sluice`, `extraction`, `optics`, `kinetic`, `network`, `automata`, `transit`, `ballistics`, `parity`).
  - **Clockwork Citadel Campaign (`epoxy_citadel`)**: 50 multi-chamber puzzle levels grouped into 5 chapters of 10 (`public/configs/citadel-levels.json` and `public/configs/citadel-campaign.json`: "Outer Sluices & Counterweights", "Cryo Ducts & Boot Tolls", "Automata Escapements & Rail Foundries", "Prism Optics & Transit Networks", and "Ballistic Sanctum & Parity Vaults"), synthesizing puzzle archetypes from across the CC1, CC2, and CC3D level corpus into 2-chamber and 3-chamber citadels with their own isolated save slot and verified replayable solutions (`O`).
  - **Chip's Challenge 2 and Chuck's Challenge 3D mechanisms** (Epoxy rules only, pack formats 13 to 17): CC2 track cells and the railroad sign, canopies, chain pushing of blocks, dynamite, green chips and bombs, steel walls, Melinda, no-signs for every item, logic gates (NAND, data latch, counter, lightning bolt), floor mimics, timid teeth, ghosts, rovers and mirror players, and in format 14 the CC2 slime (dirt and ice blocks survive it), CC2 turtle, CC2 flame jets worked by orange buttons, the popdown floor (blocks barred), the four-way arrow block, the CC2 transmogrifier, random and CC2 red teleporters and the helmet, and in format 15 the CC2 pop-up wall and open trap, red teleporters and transmogrifiers switched by wire, and the CC3D dirt, slime, appearing wall and ice block (which pushes whole lines and slides over the security gates), and in format 16 the CC2 orange button held down by any actor and the CC3D dirt block, and in format 17 the CC3D sealed trap that no button, wire or link opens and the four CC3D colour blocks (like the dirt and ice blocks of formats 15 and 16, they stop against a wall when they slide on ice instead of bouncing back); CC3D fish gate, forward and turning teleporters and the CC3D monsters (bouncer, snappy, nibble, blinky, limpy, limpa, omni, walker, legs, screamer). Levels can hold several players (one controlled at a time, `V` or a touch button swaps, all must exit): the editor has a Second Player tool, the CC2 import places every player and the validator checks each one. The CC2 import and the CC3D conversion use them, and the level editor places and configures them (tracks and per-tile hint texts in the Cell inspector, canopy brush, gate ports in the Connections rows; each CC2 hint block goes to its own hint tile). See the [Mechanisms Reference](./docs/mechanisms.md) ([version française](./docs/fr/mechanisms.md)) and the in-editor "How mechanisms work" card.
  - **Bundled Community Packs**: `Tile World Intro` and `CCLP 1` through `CCLP 5` (see [Credits](#credits)).
  - **Community packs with the classic rules**: the bundled community packs and imported `.DAT` files play on the Epoxy engine with the classic Chip's Challenge rules (monster timing, force floors, ice, teleporters and trap behaviour of the original), with every Epoxy aid: help, tap-to-path, the objective marker and the dead-end watch. Classic Chip's Challenge has no item drop, so it is off there. The Lynx engine is kept for levels made for it: packs imported before this change stay on Lynx (import the `.DAT` again to get a new pack on the Epoxy engine; scores do not carry over), and new levels are Epoxy levels: the editor's `Rules` field lists Lynx only for a level that already uses those rules, which can be switched to Epoxy.
  - **Chuck's Challenge 3D levels**: the import button also takes `.xml` level files from Chuck's Challenge 3D. Pick one or several at once and they become one pack, played on their own rules engine (`src/core/cc3d/`), beside the Lynx engine. A file that cannot be read is refused with a message that says why. The levels are not included with Epoxy: they must come from you, and they stay in your browser like other imported packs. They open in the level editor (see [Your packs and the level editor](#your-packs-and-the-level-editor)). Help, tap-to-path, the objective marker, solution replay, item drop and the dead-end watch are unavailable there.
  - **Diggy's Adventure floors (`floors_*.json`, `.har`)**: the import button and drag-and-drop also accept one or several `floors_*.json` (or `.diggy.json`) floor definition files, `.har` browser network captures or `CommandSynchronize` JSON envelopes from Diggy's Adventure and combine them into an Epoxy level pack (`src/formats/DiggyCodec.ts`). Both legacy (`blocked`) and newer (`blocked_tiles`) floor coordinate formats are decoded, along with optional runtime diggable `tiles` (`dirt`), teleport beacons (`teleport_red` to `teleport_green` and `teleport`), lever gates (`key_*` and `door_*`), light sensor beacons (`laser_emitter_*`, `mirror_slash` / `mirror_backslash`, `laser_receiver_*` and `laser_gate_*`), boulder puzzles (`dirt_block` pushed or pulled from a wall recess with `boots_pull` onto `pressure_plate_*` to open `hold_door_*`, or into `water`), and loot chips (`chip`, `socket` and `exit`). Each imported floor keeps its dimensions, is checked by a solver in `GameEngine` and is saved with its replayable solution (`O`). The floor files are not included with Epoxy: they must come from your own copy and stay in your browser.
  - **`.DAT` / `.CCL` / `.JSON` Support**: Import level packs in the widely used CC1 `.DAT` binary format via drag-and-drop (the `.DAT` export is hidden by the `foreignAuthoring` switch in `src/config/constants.ts`, off by default). Packs you own can be imported this way. Files larger than `import.maxFileBytes` (4 MiB) are refused before they are read. When the `.DAT` export is switched on, a level smaller than the 32x32 format is closed with wall, and a level that does not fit is left out with a message instead of being written wrongly. The level author stored in a pack (field 9) is shown next to the title, and the editor has an Author field. A "Delete imported packs" button next to the import button removes every imported pack at once, after a confirmation; built-in packs and your own packs are kept. A pack exported as JSON from "My packs" keeps every engine and can be imported back under its name (see [Your packs and the level editor](#your-packs-and-the-level-editor)).
  - **Sokoban collections (`.xsb` / `.sok`)**: drop a collection on the game and every level plays as Sokoban: it is won as soon as each target holds a block, with no exit to reach. Run-length rows (`4#`) are expanded, the outside of the room becomes wall, and a level the file breaks (no player, no target, fewer boxes than targets, a room open to the edge) is skipped with a count. Packs you own stay in your browser, like imported `.DAT` packs. In the editor, any level can use this rule (`Win Rule` field, `block_target` tile); such a level cannot be exported to `.DAT`. Help plays the next push and the dead-end watch covers these levels, up to `blockPuzzle.watchMaxCells` cells. Sokoban levels are drawn automatically with sprites from Kenney's Sokoban pack (cobble floor, brick walls, target marks, wooden crates) whatever graphics style is selected, while the player keeps the style's own sprite; a button next to the LCD toggle in Options > Advanced turns this skin off (on by default, saved).
  - **Levels of any size**: a `.json` level or custom pack sets its own width and height, from a 10x10 room to a 40x40 or 100x100 level (`grid.minLevelSize` to `grid.maxLevelSize` in `game.json`); the camera and the editor follow the level. The `.DAT` format and the procedural generator keep the classic 32x32 (`grid.mapWidth` / `grid.mapHeight`).
  - **Proven Procedural Generator**: Builds levels from hand-drawn puzzle pieces (`public/configs/motifs.json`), each proven fair and solvable by a solver that runs the real game engine. Every generated level is then replayed start to finish before it is offered, so it is always solvable and no puzzle can be skipped. Difficulty, focus and pacing grow with the level number. From level 3, levels are hubs with locked wings whose keys and boots lie in other wings; hub outlines (`procedural.hub.shapes` in `game.json`) and reward rooms vary, and with the biome set to Auto each level shows the theme of its main mechanic. Levels are laid out compactly, with few dead ends, and no two neighbouring levels of a pack share a main mechanic or hub outline. Each pack comes from a seed: **Endless mode** (or `N`) asks for one (empty means random) and the level to start at, and the seed of the pack being played is shown next to the pack selector with a Copy button.
  - **Endless mode**: aims at community-pack difficulty from its first level. Level 1 is already a timed hub of 7 hard pieces (up to tier 5), growing to 10 pieces and 6 motifs (`procedural.endless` in `game.json`). Only the level being played is built; the next one is prefetched in a Web Worker, and the dialog remembers the seed and the furthest level reached so a run can be resumed. The pack never ends; a run can start at any level up to `endlessUi.maxStartLevel` (10000), and `src/generator/EndlessFingerprint.test.ts` checks that a seed always builds the same levels. Hub wings can be chains of puzzles that return to the hub through a one-way force-floor strip (`hub.returnGate`), which allows irreversible pieces and removes the walk back. Keys are scarce (`hub.scarceGates`): a door colour can guard two wings while only one key is reachable at first, so the order in which wings are opened matters and the wrong door means restarting the level. Monsters appear in most levels (`procedural.endless.motifShares`). The open area of the hub is content, not bare floor: 1 to 3 monsters that move on fixed lines (`hub.openMonsters`), 4 to 9 chips scattered as route waypoints, one more per so many cells of the region (`hub.openChips`) and fire or water patches (`hub.openHazards`), with gravel aprons that keep the monsters out of the wings; the prover walks this region with a timed search. The region scales with the area the puzzles leave free: the hub outline grows by rows and columns of floor before the wings are placed (`hub.outlineGrowth`), so a level with fewer or smaller puzzles has a larger hub; the prover's region search heads for its target best first, so the proof cost follows the way, not the floor; `npm run report:hub` measures where the map area goes. Density rules keep puzzles fair: `minBoxCellsPerMonster` gives each monster room and `maxMonstersPerLevel` caps the level. Puzzles depend on one another (`hub.dependencies`): a piece exports a dirt block pushed out of its exit, which is pushed along a straight lane into the next piece, where it bridges the water that locks it; or a piece exports a key that only a door in another wing takes, so the wings must be visited in the right order. Pairs are declared in the pieces themselves (`exports` and `imports` in `motifs.json`), paired by the hub planner in loop-wing hubs only, and the whole level is replayed with the block pushed and the key carried. The library holds 169 pieces (with a piece-reuse cooldown `avoidPiecesFor` in endless mode), including monster arenas, teleport networks, toggle-wall sequences, clone machines, dirt-barrier puzzles (`dirt` motif), sanctuary sluices, counterweights, parity locks and tank/trap automata, Chip's Challenge 2 mechanics (`ice_block` alchemy, `button_orange` flame-jet airlocks, coloured teleporters, `forbid_*` gates with `thief_keys`, `recessed_wall`, `turtle` bridges, `slime` neutralizers, `button_gray` chip/bomb swaps), and the exporter and consumer pieces of these pairs (for both `dirt_block` and `ice_block`). `npm run report:levels` measures this mode against the community packs, `npm run report:dependencies` measures how many levels hold a dependency pair, and `src/generator/EndlessGuard.test.ts` keeps its width, branching, backtracking, monster presence, share of open floor near content, piece count and generation time above set floors. In block puzzles, the Help button plays the next push, and the game warns as soon as a dead end is proven (search budgets under `blockPuzzle` in `game.json`: a small one for the automatic watch, a larger one for the Help button).
  - **Solution** (`O`): every campaign and generated level stores the solution its proof replayed. The button restarts the level and plays that solution to the exit; watching it records no score.
- **Complete Tile & Monster Engine**:
  - Elemental hazards (`water`, `fire`, `ice` with corner deflectors, `force` conveyors that carry the player, blocks and monsters, `bomb`, `slime` neutralized into floor by any block).
  - Interactive mechanisms (`button_green`, `button_red` clone machines, `button_brown` bear traps, `button_blue` tank reversers, `button_gray` 5x5 chip/bomb swap, `teleport` pads, `thief`).
  - Inventory drop: `E` puts the selected key or boots down on the current cell, `C` selects the next held item, and a click on a HUD slot drops that item. Pickups happen only on entering a cell, so a dropped item stays until you come back for it.
  - Forbidden-item barriers (`forbid_key_red`, `forbid_boots_fire`, ...): the cell refuses you while you carry the item and is floor once you have dropped it elsewhere. A key thief (`thief_keys`) takes every key, as the boot thief takes the boots.
  - Turtles (`turtle`) sink into water once the player or a block has left them, so a turtle bridge is crossed once.
  - All fifteen thin-wall combinations (`thin_wall_ns`, `thin_wall_nesw`, ...), colour teleporters that chain only with their own colour (`teleport_red` to `teleport_green`), flame jets toggled by `button_orange` (`flame_jet_off` / `flame_jet_on`, fire boots protect), and bonus items: score flags (`score_10`, `score_100`, `score_1000` join the level score paid at the exit; `score_2x` doubles that level score, flags included) and stopwatches (`stopwatch_bonus` adds 10 seconds, `stopwatch_penalty` takes 10). The boots that protect you on your current cell cannot be dropped there.
  - 9 creature movement patterns (`bug`, `fireball`, `pink_ball`, `tank`, `glider`, `teeth`, `walker`, `blob`, `paramecium`).
  - Lasers (Epoxy rules only): emitters (`laser_emitter_n` to `laser_emitter_w`) cast a straight beam that kills the player and monsters; pushable mirrors (`mirror_slash`, `mirror_backslash`) turn it 90 degrees and refuse water; receivers (`laser_receiver_red`, `laser_receiver_blue`) hold the laser gates of their colour open while lit (`laser_gate_red_closed` / `_open`, same for blue). A level can be won by lighting every receiver (win rule `receivers`). Every tile declares whether the beam crosses it (`laserTransparent` in `tiles.json`). Lynx levels and DAT export refuse laser content.
  - Colour channels (Epoxy rules only): pressure plates and hold doors in red, green, blue and yellow, where a door stays open while every plate of its colour is pressed (by the player, a block at rest, or a colour block of the same colour only); colour blocks (`color_block_*`) that float in water as walkable floating blocks; red, blue and yellow toggle walls with their own toggle buttons. Play aids are off on such levels. Lynx levels and DAT export refuse them.
  - Thin walls on any terrain and hidden terrain (Epoxy rules only): `cellEdges` blocks cell edges on water, ice, force floors and the rest; `underlays` hides a terrain under a key door, socket, blue fake wall or dirt until it is removed (a key door or a socket can also hide a socket, dirt, a fake wall, a toggle wall, a hold door or a plate; the editor marks a hidden toggle wall or hold door with a square, filled when stored closed and outlined when open). Pack JSON is written as version 2 or 3 only when a level uses them. Lynx levels and DAT export refuse them.
  - Slow-time charm (`slow_time`, Epoxy rules only): while held, every monster takes twice as long per step; a thief takes it, and a fifth HUD slot appears only on levels that place it. Lynx levels and DAT export refuse it.
  - Turrets (Epoxy rules only): pushable blocks (`turret_fixed`, `turret_cw`, `turret_ccw`, `turret_multi`) that fire a 3-cell beam killing the first player or monster it reaches; the rotating ones turn every 60 ticks, a turret faces the way a player pushes it, and turrets fire after the player's first step. Lynx levels and DAT export refuse them.
  - Swivel doors, speed boots, truesight boots, grappling gloves and the transmogrifier (Epoxy rules only): swivel doors (`swivel_door_ne`, `swivel_door_se`, `swivel_door_sw`, `swivel_door_nw`) are entered and left through their two open sides and turn a quarter turn when something leaves, closing the side it came in by; speed boots (`boots_speed`) halve the player's walking cooldown while held; truesight boots (`boots_eye`) draw invisible and appearing walls with a marker while held; grappling gloves (`boots_pull`) pull a stationary block behind the player when stepping away from it, unless the block rests on an active plate, brown button or block target; the transmogrifier (`transmogrifier`) swaps a monster that arrives on it for its pair (bug and paramecium, glider and fireball, teeth and skitter, pink ball and walker), and switches a player who steps on it between Chip and Melinda. A thief takes any of these boots. Lynx levels and DAT export refuse them.
  - Puppets and skitters (Epoxy rules only): a puppet (`puppet`) never moves by itself; when the player's step ends on a puppet control (`puppet_control`), every puppet steps the same way, pushing a block and pressing plates; a skitter (`skitter`) flees the player. Play aids are off on levels with puppets. Lynx levels and DAT export refuse them.
  - Shot launchers (Epoxy rules only): `shot_launcher_n` to `shot_launcher_w` fire a shot each time a linked shot trigger (`shot_trigger`) is pressed (a trigger with no link fires nothing); a shot kills the player and monsters, melts ice blocks, sets off bombs, destroys turrets and is deflected by mirrors. One-sided mirrors (`one_sided_mirror_ne` to `_sw`) reflect on their front faces only, and a shot from behind destroys them. Lynx levels and DAT export refuse them.
  - Arrow blocks and turn plates (Epoxy rules only): four pushable arrow blocks (one way, two ways, corner, three ways) move under a push only toward a side that shows an arrow; slides, teleports and clone machines move them whatever their arrows and never turn them. Two turn plates turn an arrow block a quarter turn, clockwise or counter-clockwise, each time it arrives on them by a push, a slide, a teleport or a clone machine; nothing else turns. The editor rotates them with the direction control. Ice blocks and arrow blocks also push a line of blocks (CC2 rule): an ice block moves ice blocks and arrow blocks, an arrow block moves dirt, ice and arrow blocks, a wall at the end, the map edge or a sliding block in the line refuses the whole push, and a puppet, pull boots, slides and clone machines never chain. A level where this can happen is written as pack format 13, and the push hint and dead-end watch are off on it. Lynx levels and DAT export refuse them.
  - Turning force floor (`force_cycle`, Epoxy rules only): a force floor with no fixed direction. It pushes east, then south, west and north in turn, and the turn is shared by the whole level: every arrival of the player, a block or a monster on any such floor takes the next direction. Force boots cancel the push but the arrival still counts. Lynx levels and DAT export refuse it.
  - Ward and lurker (Epoxy rules only): a ward (`ward`) is boots you can drop like any other. The first monster that touches you, or that you walk into, is destroyed and the ward is used up; it gives no protection from bombs, shots, beams, water or fire, and a second ward stays on the floor while you wear one. A sleeping lurker (`lurker_dormant`) looks like plain floor with a faint seam and never moves; when you arrive on a cell orthogonally next to it (a step, a slide through that cell or a teleport), it wakes as a lurker (`lurker`) that, after a short pause, chases you slowly and never sleeps again. Touching a sleeping lurker kills. The editor shows a sleeping lurker with a faint marker, and the validator warns when one is not on plain floor. Lynx levels and DAT export refuse both.
  - Wisp (`wisp`, Epoxy rules only): a see-through monster that drifts straight ahead through every tile (walls, doors, water, fire, ice, force floors, teleporters): terrain has no effect on it and it presses no plate. Only a thin wall, the map edge or any other entity (a monster, a block, a mirror, a turret) stops it; it then turns round once, and stays put if it is blocked both ways. It kills on contact (a ward absorbs the contact) and dies to a shot, a laser beam, a thrown stone, a blast or a ward. It cannot be cloned: the validator reports one on a clone machine or in a clone link. Lynx levels and DAT export refuse it, and a pack that uses it is written as pack format 10 (this build reads formats 1 to 17).
  - Blast charge (`charge`, Epoxy rules only): an item you pick up and carry as a count (shown in the boots grid). The drop key (`E` or `X`), a click on its slot or, on a phone, the drop button in the corner beside Undo puts one down on your cell as a lit charge (`charge_lit`). Sixty ticks later (three seconds, `timing.chargeFuseTicks`) it blasts: every monster and block within one cell of it, diagonals included, is destroyed, and so is the player if standing there (a ward does not help). Terrain, items, bombs, other lit charges and the template creature on a clone machine stay. A lit charge blocks nothing and cannot be picked up or pushed; the blast is counted in game ticks, so slow-time boots do not stretch it. A stored solution writes the drop as `X`. The push hint and the dead-end watch are off on a level with a charge, and block searches give no verdict there. Lynx levels and DAT export refuse it, and a pack that uses it is written as pack format 7 (this build reads formats 1 to 17).
  - Pocket gate (`pocket_gate`, Epoxy rules only): an item you pick up and carry as a count (shown in the boots grid). The drop key (`E` or `X`), a click on its slot or, on a phone, the drop button in the corner beside Undo sets one down on your cell as a pad (`pocket_gate_pad`), but only on plain floor with no item on it, with nothing hidden under it; anywhere else the drop is refused. Setting a pad down on your own cell causes no jump. Pads never mix with the other teleporters: they link only with each other, wherever they are, whether placed in the editor or set down in play, and the walk is read live from the map in reading order (row by row, left to right). A jump leaves from the previous pad in reverse reading order, wrapping from the first to the last, the way the other teleporters do; a single pad does nothing, blocks and monsters use the pads too, and a pad stays for good (it cannot be picked up again; undo fixes a misplaced one). A blast leaves the pads standing, and a key thief leaves gates in the pocket. A stored solution writes the drop as `G` (`X` stays the blast charge). The push hint and the dead-end watch are off on a level with a gate or a pad, and block searches give no verdict there. Lynx levels and DAT export refuse both, and a pack that uses either is written as pack format 8 (this build reads formats 1 to 17).
  - Rails (Epoxy rules only): eight rail pieces laid as terrain, two straight (`rail_ns`, `rail_ew`), four bends (`rail_ne`, `rail_se`, `rail_sw`, `rail_nw`) and two rail switches (`rail_switch_a`, `rail_switch_b`). A piece is open on two sides and closed on the other two: walkers (the player and monsters), sliders, blocks and teleport exits get into or out of its cell only through an open side, so a closed side stops them from the neighbouring cell too. A monster that comes in by an open side turns to the other open side, so a forward move follows a bend; the bug and the paramecium, which turn toward a wall side first, keep their own turn order instead and meet a closed side as a wall. A monster dropped on a rail by a teleport or a clone keeps its facing. Beams and shots pass over rails untouched. The two switches are bends (south-east and south-west) that swap into each other each time a green button is pressed. In the editor, `R` turns the rail piece being placed (a fixed piece a quarter turn clockwise, a switch to its twin), and the validator notes a rail switch on a level with no green button. Lynx levels and DAT export refuse rails, and a pack that uses them is written as pack format 9 (this build reads formats 1 to 17).
  - Hurl Stone (`hurl_stone`, Epoxy rules only): an item you pick up and carry as a count (shown in the boots grid). The drop key (`E` or `X`), a click on its slot or, on a phone, the drop button in the corner beside Undo throws one at the cell ahead of you instead of setting it down. The stone flies straight, a cell per tick (`timing.hurlStepTicks`), until it hits something: it kills a monster, sets off a bomb and melts an ice block, and a mirror turns it (from the back of a one-sided mirror it destroys the mirror instead); if a mirror sends it back at you, it kills you (a ward does not help). Any other block, a wall, a thin wall, the map edge or an item other than a bomb stops it. It is single-use: it is gone where it stops. The throw is refused, with the stone kept, while you slide or are still in the pause after a step, and when the cell ahead would stop it at once. You cannot step into a stone in flight. A stored solution writes the throw as `T`. The push hint and the dead-end watch are off on a level with a stone. Lynx levels and DAT export refuse it, and a pack that uses it is written as pack format 10 (this build reads formats 1 to 17).
  - Wired flip (Epoxy rules only): a signal link can end on a green toggle wall (`toggle_wall_closed`, `toggle_wall_open`) or a rail switch (`rail_switch_a`, `rail_switch_b`), and that one cell flips to its other form each time the signal starts sending (a rising edge; the moment it stops does nothing). The green button (`button_green`) still flips the same cell, so the two can be mixed; a flip tile hidden under a removable top is never wired. Lynx levels and DAT export refuse a level with such a link, and a pack that has one is written as pack format 11 (this build reads formats 1 to 17).
  - Relay pad (`relay_pad_dark`, `relay_pad_lit`, Epoxy rules only): a pad that a signal link ends on takes the form of its signal, lit while the signal is on and dark while it is off; a pad no link ends on keeps the form it was placed in. A dark pad is plain floor. A lit pad is a teleporter of its own group: it sends whoever steps on it (a block or a monster too) to the previous lit relay pad in reading order (row by row, left to right), wrapping from the first to the last, and a lit pad alone does nothing. Relay pads never mix with the other teleporters. A pad that lights under someone makes no jump (a jump happens on arrival only), and a pad that goes dark leaves them standing. Lynx levels and DAT export refuse both, and a pack that uses either is written as pack format 11 (this build reads formats 1 to 17).
  - Toll Token (`toll_token`, Epoxy rules only): an item you pick up and carry as a count (shown in the boots grid). The first time you step onto a boot thief or a key thief that would take something from you, one token is spent instead and the thief takes nothing; one token pays for the whole visit. A thief with nothing to take leaves the token alone, a thief never takes a token, and it cannot be set down. Lynx levels and DAT export refuse it, and a pack that uses it is written as pack format 11 (this build reads formats 1 to 17).
  - Signals (Epoxy rules only): a signal plate (on while something stands on it) and a signal button (a pulse: on for one moment each time something steps on it) and AND, OR, NOT, XOR and latch gates send a signal along links to coloured hold doors, which open while their signal is on. A signal can also end on a shot launcher or a clone machine, which fires once each time its signal starts (use a latch between a button and a hold door, since a pulse alone opens the door for one moment only). Every signal tile is drawn with its powered state and its links. Lynx levels and DAT export refuse them.
- **Visual & Tactile Enhancements**:
  - An optional character skin (Options > Advanced > Character: Standard or Julien) redraws the player in every graphics style; Standard is the default and the choice is saved.
  - HD Neon, 16-Bit Retro and 32-Bit Retro pixel renderers (chosen in Options > Essential, or cycled with `G`) with 4 biome themes (`Cyber Neon`, `Arctic Lab`, `Magma Core`, `Lynx LCD`): walls join into continuous masses that cast soft shadows, light sources glow in HD Neon, 16-Bit Retro draws every tile and character as a 16x16 sprite in a 9-bit console palette (with an optional LCD grid), 32-Bit Retro uses 32x32 shaded sprites in 15-bit colour (lighting and shine are drawn on top), and the player and every monster are animated. A graphics quality setting (Auto by default) keeps the game smooth on slower devices.
  - Runeward and Runeward Parchment (chosen in Options > Essential, or with `G`): a drawn dungeon with stone floors and walls, animated water and lava, a glowing exit and a mage player; Parchment draws the same dungeon as ink on aged paper. Every tile, item, block and monster has its own drawing (eleven original creatures for the monster types), with the colour-blind glyphs kept; only tiles of imported CC3D levels keep the shared drawing.
  - Five Retro HD styles (Pocket 4-tone, Pastel, Blueprint, Sepia and Classic 90s) draw the same full-resolution scene as HD Neon with a palette of their own, flat colour bands instead of smooth gradients, no glow and a light texture on top (dot grid, grid lines, paper grain, scanlines). Fire, water, ice, traps, monsters, keys and doors keep their own colour family in each of them, so they stay easy to tell apart.
  - **Hint** (`H`): dynamic objective locator and mechanism link overlay; hovering a colour teleporter shows its own network, and hovering an orange button shows the flame jets it toggles.
  - Colour-blind glyphs on coloured doors, keys, buttons and colour teleporters.
  - Reduced motion: with the system setting on, the hop, bob, glints, flicker, blinking, particles and screen shake rest, and a change of the setting is followed live.
  - Keyboard: `Tab` moves focus between the controls, Ctrl/Cmd chords are left to the browser except undo (Ctrl/Cmd+Z), which follows the keyboard layout (AZERTY, QWERTY, Cyrillic...), and `?` opens the help.
  - Full smartphone touch support: in full screen on a phone, a floating joystick appears under the thumb anywhere on the board (hold to keep walking; a tap walks to that cell), and a fixed pad stays available through the Touch control setting in Options. Vibration can be turned off. The zoom is set in the options. The play board is landscape everywhere except in the mobile portrait layout, which keeps a square board: the zoom option sets the number of rows shown, a level smaller than the view is zoomed up to 1.5 times, and the space around the level shows a darkened wall colour.
  - Phone full screen layout: the board fills the screen under a top strip showing the level, the chips and the time. The strip tabs open two drawers: the level panel (with the held items) on the left and the game menu on the right. Undo and the drop buttons sit in a corner, on the pad side chosen in Options. The camera keeps the player clear of the pad.
  - Full-featured Level Editor with live solver validation, and your own level packs (see [Your packs and the level editor](#your-packs-and-the-level-editor)).
- **Music**: seven original music tracks by Julien Bombled (see [Credits](#credits)), with three modes, chosen in Options > Advanced (sound on/off stays in Options > Essential). **Default** follows the biome on screen (each biome names its track with `musicTrackId` in `game.json`). **Random** picks a new track for each new level and never repeats the previous one while two or more tracks exist. **Custom** does the same among the tracks you tick (at least one stays ticked). A restart, a retry after dying or a one-level wrap does not change the track, and in Random and Custom the biome (and the `B` key) no longer changes the music. The mode and the ticked tracks are saved.
  - The game ships seven original tracks: `8-bit Odyssey` for Cyber Neon, `Subterranean Pulse I` for Arctic Lab and `Subterranean Pulse III` for Magma Core (`Subterranean Pulse IV` is only in Random and Custom). Retro Lynx LCD plays `Subterranean Pulse II`. These seven tracks are the only music: nothing is synthesized any more.
  - Volume: two sliders in Options > Essential, "Effects volume" and "Music volume", from 0 to 100 % in steps of 5, each shown while its sound is on. 100 % is the loudness set in `audio.json`; the music slider applies to the playing track at once. Both values are saved.
  - In Default mode, the levels of an endless run play `Endless I` or `Endless II` instead of the biome track: a new level never repeats the track of the level before. The list is `endlessUi.musicTrackIds` in `game.json`. Random and Custom are unchanged.
- **Sound effects**: most effects play bundled CC0 audio files (see [Credits](#credits)), with the synthesized sound as fallback until a file is decoded or when it fails. Footsteps depend on the terrain the player steps onto (floor, force floor, ice, and water or fire with the protecting boots), mapped by `terrainStepEffects` in `audio.json`. Under the Lynx rules, only a step the player chooses makes a sound.

## Your packs and the level editor

- **My packs**: the "My packs" button in the header (also in the drawer, the Levels dialog and the editor's "Open...") lists your packs. Create and rename packs, then play, export or delete them. Levels are stored in your browser (IndexedDB).
- **Per level**: reorder, edit, play, duplicate, copy or move to another pack, delete. Badges show each level's engine (Epoxy, Lynx, CC3D, Sokoban). CC3D levels can be managed and edited, and a "Convert to Epoxy" button on their rows saves a native Epoxy copy after a report of what plays exactly, approximately or not at all (the rules differ, so the copy may not be solvable; the original is never changed).
- **Export**: a complete JSON file that keeps every engine, or a `.CCL` file. A JSON file exported this way can be imported back with its name.
- **Delete a pack**: asks for confirmation with the number of levels, and offers "Export first". "Delete imported packs" never touches your own packs.
- **Thumbnails and order**: every level and pack shows a small map. Drag a level by its handle to reorder it (mouse or touch; `Escape` cancels), or use the arrow buttons or the arrow keys on the handle.
- **Author and description**: each pack can carry an author and a description, edited in the pack header and kept in the JSON export.
- **Share a pack as a link**: "Copy share link" puts the whole pack in the link itself, after the `#`, so it is never sent to a server. Whoever opens it sees a preview (name, author, levels, engines, thumbnails) and chooses Import, Import and play or Cancel; nothing is stored before that. A pack already imported from the same link is recognised. Links are limited to `share.maxLinkChars` characters (a few levels); export the JSON file for bigger packs, since long links do not fit every chat app.
- **Imported level ids**: levels of an imported file get ids unique to their pack, so importing the same file twice, or a file named like a built-in pack, no longer mixes their records. Duplicates already stored are renamed once at load; the first copy keeps its records.
- **Your previous Custom levels** were moved automatically into a pack of yours ("My levels"); there is nothing to do.
- **Layout**: palette, canvas and level settings sit in three columns on wide screens, two on medium ones and one on narrow ones or tall portrait tablets, where the palette becomes a horizontal strip; the Mechanisms tab groups its entries under sub-headings (buttons and links, teleports, lasers and mirrors, colour channels, blocks and turrets, flames and toggles), and hovering or choosing a palette entry says what it does and what it needs (for example, a hold door needs a pressure plate of its colour); the search field above the palette (`/`) filters every tab at once by name and description, ignoring accents, and the palette is a single Tab stop with the arrow keys, Home and End moving along its entries. The canvas is scaled to fit the window; zoom with `-`, `+`, `Ctrl` + wheel or the zoom buttons, and `0` or "Fit" to fit again; the coordinates badge describes the cell under the pointer. On a touch screen one finger edits, and two fingers pan the map and pinch to zoom (a stroke just begun is taken back), and holding a finger still picks the tile under it. A zoom keeps the cell under the pointer in place, the keyboard cursor scrolls a large map along, and undo and redo show where the change was and say what it was.
- **Tools**: Brush (`B`), Fill (`F`), Eraser (`E`) and Picker (`I`; Alt+click or middle click also picks). `R` rotates the facing of the selected creature or player start, `Shift`+`R` turns the creature or turret under the cursor a quarter turn clockwise (one undo step), `K` starts linking the device under the cursor (a brown or red button, a trap, a clone machine, a shot trigger, a shot launcher, a signal plate or button, a gate, a laser receiver or a hold door: click a partner or press `Space` on it to link or unlink it, or an empty floor cell to place a new partner already linked; `Escape` or the Done button ends it), and `Escape` also cancels a pending paste or drops the selection. A clone machine shows the creature it clones, with its facing, as a corner badge; its link follows the creature standing on it whenever you paint, fill or turn one there, and the status line says so (linking a red button to a clone machine with no creature warns that the default block is used). Palette icons of creatures and turrets follow the direction control, and the cell description speaks a turret's facing and what a clone machine clones.
- **Without a mouse**: focus the canvas, move the cursor with the arrow keys and paint with `Space` or `Enter`; a screen reader is told what the cell holds once the cursor stops.
- **Check badge**: shows Valid, the number of warnings or the number of errors for the level. The Issues section of the inspector lists them (errors first, up to 100) and updates as you edit; an issue that names a cell is a button that moves the cursor there and scrolls it into view.
- **Draft recovery**: while a level has unsaved changes, the editor keeps a draft of it in your browser (written a moment after you stop editing, and when the page is hidden). After a crash or a closed tab, the next visit offers to restore it, discard it or decide later; restoring on top of a stored level keeps undo going back to the stored version, and a warning says when the level changed in its pack meanwhile. A draft above `1 000 000` characters is skipped, with a message. Each tab keeps its own draft, so two open tabs never overwrite each other; the drafts of closed tabs are offered one at a time, newest first.
- **Level settings** come in sections: Level, Rules (with the engine), Size (resize a level around a 3 x 3 anchor picker, top-left by default; the same under Epoxy and Lynx rules) and Generate. Under Lynx rules the Epoxy-only items of the palette are disabled (lasers, mirrors and colour channel tiles: plates, hold doors, colour toggle walls and buttons, floating blocks, colour blocks), with a one-click "Switch this level to Epoxy". Thin walls on cells (`cellEdges`) are drawn on Epoxy levels and kept through every edit, copy, move, resize, save and autosave; a level that has some cannot be switched to Lynx. The terrain hidden under a removable tile such as a door (`underlays`) is kept the same way, drawn as a corner marker and spoken with the cell; painting a tile that cannot hide it over its cell, or erasing the cell, removes it and the status line says so. To set it, put the cursor on such a tile and pick a terrain in the Hidden terrain list of the Layers section (None clears it): one undo step, not available under Lynx rules. The links from shot triggers to shot launchers (`launcherLinks`) are kept through every edit, copy, move, resize, save and autosave, drawn as a magenta line, and dropped with their cell when either end is overwritten or erased; a level that has some cannot be switched to Lynx. The shot launchers and the shot trigger are in the Lasers and mirrors group of the Mechanisms tab, and the links between them are made in a link session (`K`, or Link... in the Connections section, from either end; Epoxy rules only). One trigger can fire several launchers and one launcher can be fired by several triggers; each change is one undo step, and painting another facing over a launcher keeps its links. The cell description tells how many launchers a trigger fires and how many triggers fire a launcher. The Terrain tab ends with a Thin Wall entry (Epoxy rules only, greyed under Lynx): a click toggles the side of the cell nearest the pointer, drawn as a bar before you click (by keyboard, the side of the direction control), one step per click. A wall is one line shared by two cells: if either cell closes the side, the click removes it from both. The eraser clears only the thin walls stored on its own cell, and a neighbour's matching wall stays; the screen reader description of a cell lists the sides that are closed. Undo and redo also cover the settings and the engine, and the unsaved mark clears when you undo back to the saved state.
- **New**: start from an empty room, an empty CC3D room, a Sokoban room, a laser puzzle, or nine sanctuary mechanism rooms (`boulder_sluice`, `counterweight_hold`, `grappling_alcove`, `prism_slalom`, `elemental_alchemy`, `rail_switchyard`, `monster_clock`, `turning_force`, `hurl_stone_ricochet`; templates in `public/configs/templates.json`, Epoxy only; a pack made mostly of Lynx levels offers the empty rooms).

Each row has a "go to" button, and a link row has an Unlink button (one undo step; the status line says what the trap or the red button does now). On any end of a link (a brown or red button, a trap, a clone machine, a shot trigger or launcher, a signal plate or button, gate, laser receiver or hold door), "Link..." (or the `K` key) starts a link session without touching the tool or the brush: the device is outlined, the partners it can link to are outlined in the mechanism colour and its links are drawn as arrows; click a partner to link or unlink it, or an empty floor cell to place a new partner already linked, each change being one undo step. The section stays on that device and the button reads Done; Escape, Done or another tool ends the session. Under Lynx rules a button keeps one link per mechanism (a new link replaces the old one) and shot devices are not available. The list does not change while the focus or the pointer is inside the section, or during a brush stroke. On the map, the hovered and cursor cells draw arrows to what they work and from what works them, in the colour of each mechanism. On CC3D levels the section lists the links derived from where things stand (the ones the map draws; no Unlink, no Link...; a device under a door, socket or false wall is said to work only once the player has opened that cell and stepped onto it) and the closed card below it shows the CC3D mechanisms and the top layer rule; under Lynx rules it says where connections are listed. A closed "How mechanisms work" section below it gives one short row per mechanism (how its parts find each other and what an unlinked part does) and the keys K, T, L, Shift+R and Shift+F.
- **CC3D levels** open in the same editor, with their own palette (Floors, Devices, Blockers, Items, Creatures, Player; colour, corner and mirror choosers; the direction control sets facings; the search field there matches names only). The eraser removes the topmost thing of a cell (creature, then item, then top layer) and `Shift`+eraser clears the whole cell. With the thin wall entry selected, a click toggles the side of the cell nearest the pointer (by keyboard, the side of the direction control). Hovering a device, or putting the cursor on it, draws its links (trap control to trap, teleport, clone switch to machine and template, laser controller to shooter, same-colour groups), and the status line says when an edit changes a link. The inspector lists the layers of the cursor cell, each with a remove button; the engine is read-only and the win rule and chips fields give way (chips are the fish on the map). Fill replaces a layer entry across a region, bounded by thin walls; the selection copies, cuts, pastes and moves rectangles (creatures keep their order, and links that change are reported); resize keeps the cell of a 3 x 3 anchor picker fixed (top-left by default). The Export XML button (Chuck's Challenge 3D's own XML format) is hidden unless the `foreignAuthoring` switch is on, and Import opens such a `.xml` file; CCL export is refused for CC3D levels. Saving a CC3D level that has errors asks first.

## Development

Requires Node.js 24 (see `.nvmrc`).

```bash
npm install
npm run dev
```

### Adding music tracks

Tracks are declared in `public/configs/audio.json` under `tracks`. A track is streamed from audio files (`"source": "file"`):

```json
{
  "id": "my_track",
  "i18nKey": "app.music.my_track.label",
  "source": "file",
  "files": ["my_track.ogg", "my_track.mp3"],
  "gain": 0.8
}
```

- Put the files in `public/audio/music/` (the folder is `musicBaseUrl`). The browser plays the first file in `files` it can decode; the extension must have a MIME type in `fileMimeTypes` (`ogg` and `mp3` by default). `gain` scales the track against the music volume (1 when omitted).
- Add the track name to `src/locales/en.json` and `src/locales/fr.json` under `app.music.my_track.label`.
- Map it to a biome with `"musicTrackId": "my_track"` on the theme in `game.json`. Every track also takes part in the Random and Custom modes.
- A file track that fails to play is skipped until music is turned back on. When no track can play, music stays silent: there is no fallback tune.
- The configuration is checked when the game loads: duplicate ids, a track that is not a file track or has no files, an unknown `musicTrackId` or an unknown `defaultMusicMode` stop the game with a clear message.

### Adding sound effects

Each effect is declared in `public/configs/audio.json` under `effects.<id>`. An effect is synthesized from `waveform` and `notes`, and can also play audio files:

```json
"teleport": {
  "files": ["sfx_movement_portal5.wav"],
  "maxDurationMs": 400,
  "fadeOutMs": 150,
  "gain": 0.4,
  "waveform": "sawtooth",
  "notes": [
    { "freq": 330, "durationMs": 35, "gain": 0.4 },
    { "freq": 495, "durationMs": 35, "gain": 0.4 },
    { "freq": 742, "durationMs": 45, "gain": 0.45 },
    { "freq": 1113, "durationMs": 60, "gain": 0.4 }
  ]
}
```

- Put the files in `public/audio/sfx/` (the folder is `sfxBaseUrl`, `./audio/sfx` when omitted) and list their names in `files`. With several files they play in turn, so the step alternates between its footsteps. A file that fails to load or decode is skipped.
- `gain` (1 when omitted) is the loudness against the master volume times the sfx volume; the shipped files use 0.4, except `blocked` (0.25) and the footsteps (0.2 to 0.45, calibrated so the quieter Kenney recordings play at about half the loudness of the other effects).
- `minIntervalMs` (no limit when omitted) skips a call made less than that long after the previous start of the same effect, on the audio clock; `blocked` ships at 250 so holding a key against a wall does not machine-gun.
- `maxDurationMs` stops the playback there. `fadeOutMs` adds a linear fade that ends at that cap; it requires `maxDurationMs` and cannot be larger than it.
- `waveform` and `notes` stay required: they are the fallback, played when no file is decoded yet (the first sounds right after the audio unlocks) or when a file is missing or fails.
- 17 of the 19 effects use files; `splash` and `burn` stay synthesized.
- `terrainStepEffects` maps a terrain to the effect id played for a step onto it. The key is the tile's `slideType` or `hazard` (`force`, `ice`, `water`, `fire`); any other tile, and a terrain without an entry or whose effect does not exist, plays `step`. Water and fire only count when the player wears the protecting boots; without them the tile keeps the normal step and the splash or burn sound follows on its own. A force floor counts even when the boots cancel its push.
- Safari versions that cannot decode Ogg Vorbis cannot play the footstep files and fall back to the synthesized step.
- `teleport` (400 ms cap, 150 ms fade), `thief` (500 ms cap, 150 ms fade) and the footsteps (`step` and `step_fire` 120 ms cap and 30 ms fade, `step_force` and `step_ice` 150 ms and 50 ms, `step_water` 180 ms and 60 ms) use a cap and a fade.

## Building a Campaign with the Generator

1. Open the **Level Editor**, set a **Difficulty**, leave **Seed** empty and press **Generate**. The seed used is written back, so the same level can be generated again.
2. Retouch the level, then **Test** it.
3. **Export JSON** and paste the exported object into the `levels` array of `public/configs/levels.json`. Exported levels load as they are; set `number` to the position you want.

A `.json` level is a blueprint: `terrain` (a grid of tile ids) or `rows` (legend strings, see `legend` in `levels.json`) gives the level its size, so rows of 40 characters make a 40-wide level; a blueprint with neither gets the default 32x32. The player start, entities and links must lie within that size.

Generator difficulty is derived from a profile (`src/generator/DifficultyProfile.ts`): `profileFor('pack' | 'endless', levelNumber, cfg)` gives the piece count, motif count, hardest tier, layout, timer and target length. Packs follow the learning curve of `procedural`; the endless mode follows `procedural.endless`. The campaign and pack mode are unchanged by the endless work.

The Epoxy campaign is written by hand in `public/configs/levels.json`. Each level's solution is described as a route in `tools/campaign-routes.json`: explicit moves (`N`, `E`, `S`, `W`, `.` to wait) for pushes and timing, and `@x,y` steps that walk to a cell along a path found by a search in the real engine. `npm run route:campaign` expands the routes and writes each solution into `levels.json` (`EPOXY_ROUTE_LEVEL=<id>` for one level). `npm test` replays every solution, checks that the exit stays out of reach without each item listed under `requires`, and checks the chapters in `public/configs/campaign.json` (every level in exactly one chapter, titles in both languages) and the pacing in `tools/campaign-rhythm.json`: the level where each tile, item or entity first appears, and timer margins. To compare the campaign with a reference pack you own, run `EPOXY_REFERENCE_DAT=<path> npm run report:originality`; the closest pairs go to `local/originality.md`, which is never committed. `npm test` also keeps every campaign level unlike every other one with a room fingerprint (the open cells, blocks and targets of the room; walls only bound it; any rotation, reflection and translation), threshold `maxRoomSimilarity` in `campaignGuard` of `game.json`. `maxSokobanSimilarity`, in the same section, applies only to the `EPOXY_REFERENCE_XSB` check below. The classic Sokoban collections cannot be bundled; to check the campaign rooms that have targets against a collection you own, set `EPOXY_REFERENCE_XSB=<.xsb/.sok/.txt file or folder>`: the otherwise skipped test in `CampaignRoomOriginality.test.ts` then runs, and `npm run report:originality` writes the closest matches to `local/originality-sokoban.md`, also never committed.

The Epoxy pilot pack is a second built-in pack used to try a rebuilt campaign on fresh players without touching the current campaign or its progress. Its levels are in `public/configs/pilot-levels.json` (ids start with `epoxy_p_`), its chapters in `public/configs/pilot-campaign.json`, its routes in `tools/pilot-routes.json` and its pacing in `tools/pilot-rhythm.json`. It is listed in the pack selector and the Levels dialog only while Playtest mode is on; turning the mode off while playing it returns to the campaign. `npm run route:pilot` expands its routes (the same tool as `route:campaign`, also reachable with `EPOXY_ROUTE_PACK=pilot`), `npm run report:difficulty:pilot` measures it, and `npm test` runs the same design and originality checks on it as on the campaign. A pilot level that deliberately reworks an old one carries `"reworkOf": "<old level id>"`, which exempts exactly that pair from the room comparison with the campaign; remove it once the level has changed enough to pass the comparison without it (the test pins the similarity). The pilot keeps its own resume point, so playing it never moves the campaign one. Chapter 2 (levels 16 to 20) teaches pushing blocks; a pilot level with blocks may declare `"blockBudget": { "waters": n, "targets": m }`, a design note that the level holds exactly n + m blocks (the waters to fill plus the targets to cover, none spare), checked by the tests.

New puzzle pieces go in `public/configs/motifs.json`; run `npm run annotate:pieces` afterwards to precompute each piece's solution and reversibility into `public/configs/motif-annotations.json`, which the generator uses instead of searching in the browser.

Sokoban rooms: `npm run forge:sokoban` builds original ones backwards from their solution (blocks onto brown buttons that hold the exit traps open). `npm run import:sokoban` adapts a collection in the standard `.xsb` format (set `EPOXY_SOKOBAN_FILE` and `EPOXY_SOKOBAN_CREDIT`); only use collections whose licence allows reuse, and keep the credit. The entry and exit tunnels are carved on any side of the room, the exit opening where the player can stand once every box is home, and the import report lists why each rejected level was not kept. Both write candidates to `local/` for curation. `npm test` checks that each one is solvable in every orientation, that no block can escape through its ports, and that nothing in it is decorative; `npm run report:pieces` writes each piece's solution to `local/piece-probe.txt`.

## Tests

```bash
npm test
```

The suite includes `src/test/typographyGuard.test.ts`, which scans every tracked text file for banned typographic characters (dashes, curly quotes, one-character ellipsis, non-breaking spaces, ligatures).

Tests run in Node by default. A test file that needs a DOM starts with `// @vitest-environment happy-dom` (shared helpers in `src/test/domFixture.ts`). Generation time budgets are measured as CPU time, so they hold when the whole suite runs in parallel.

`npm run report:levels` measures 200 generated levels against the bundled community packs and writes `reports/level-metrics.json`, including playfield metrics: fill (open cells over their bounding box), open share, dead ends, junctions, symmetry and monster presence. `npm run report:study` describes how the community packs combine mechanics, and `npm run mine:pieces` searches for harder puzzle pieces (about half an hour); both write to `local/`.

The engine golden (`engineSimHash`) hashes a tick-by-tick play of every shipped Epoxy level; set `EPOXY_SIM_GOLDEN` to a golden file to compare against it (written only with `EPOXY_SIM_GOLDEN_WRITE=1`), otherwise a determinism check runs. The CC3D coverage report (`epoxyCoverage`) classifies each element of a Chuck's Challenge 3D corpus as exact, approximate or lost on the Epoxy engine: set `CC3D_CORPUS_DIR` to the map folder and `CC3D_COVERAGE_REPORT` to the output file.
